# Custom chat (ZHU's own chat)

**Custom chat** (the **+** on the chat tab strip) opens a chat that ZHU draws itself: a conversation with any model of the providers connected under Settings → AI models. It is a tab like the website tabs, but it has no webview, no sign-in page, and nothing is typed into a third-party page. This is where the AI models you connect answer. **Send to chat** on a question, or **Add to …** on a screenshot, opens one by itself when no chat tab is open.

## What it does

* **Model per message.** The chip in the message box lists the models of every connected provider, grouped by provider, with a search box. **Free models only** is on by default; switch it off to see the paid ones too. The whole conversation is sent as context with each message, so the model can be changed between turns.
* **Free models are recognized automatically** when a provider is connected, including a provider you add yourself. How: [PROVIDERS.md](PROVIDERS.md#which-models-are-free).
* **Start without a key.** With no provider connected, **Start without a key** connects Kilo Gateway and Pollinations, which answer without an account. Their model providers may log what is sent; the screen says so.
* **Answers are typed out** as they arrive, at an even pace, as Markdown: headings, lists, tables, highlighted code with a copy button, and LaTeX. Half-written syntax never flashes on screen (a table appears once its header is complete, a formula once it is closed). A reasoning model's thinking is shown folded under "Thinking…" / "Thought it through". With **Reduce motion** on in Windows, text appears as it arrives, without typing.
* **Stop**, **Answer again** (replaces the last answer, with the model currently selected) and **Try again** after an error. A provider's error message is shown in the answer bubble, with its retry time when it sent one.
* **Conversations are kept** in the local database. **New chat** starts another in the same tab; the clock button reopens or deletes earlier ones. Closing a tab does not delete its conversation.
* **Detected questions** reach a Custom chat tab the same way they reach website tabs: the question is placed in the message box, and you press Send.
* **Screenshots** are attached by dragging them from the panel on the right onto the message box, or with a screenshot's **Add to …** button (it goes to the chat tab that is shown, or to a new Custom chat when no tab is open); new captures are attached automatically while that option is on. They are sent with the message to models that read images. In the model list, small icons after each name show what the model takes, as its provider's list states it: images, documents, audio, video, or **T** for text only; the chips under the search box explain the icons and, when clicked, show only those models. A provider that does not say gets no icons. ZHU itself sends text and screenshots only. Choosing a model also makes it that provider's model in Settings, and the model a new Custom chat starts with. A gateway (Kilo Gateway, OpenRouter) offers models that read images next to text-only ones, and its model list says which is which: with a text-only model selected, the message box says so and offers a model of the same provider that reads images (a free one when the selected model is free). Other providers do not say; there ZHU cannot know, and when the selected provider is not set to read images, the message box says so and offers **Allow images**. Earlier turns go along as text; only the new message carries its images.
* **Your resume** (bottom of the panel on the right), while switched on, is given to the model with every message as a short profile made from it once, so questions about you are answered from it; so is **the job** you are applying for, when you added one. See [Resume](#resume).

## Privacy

A message goes to the provider whose model is selected, with the earlier turns of that conversation, its attached screenshots, and your resume and the job while they are switched on, when you press Send. Nothing is sent before that: placing a detected question or a screenshot in the message box is local. The system prompt is fixed ("You are a helpful assistant in ZHU…"); the "How answers should sound" text from Settings is not added here. Conversations are removed by **Delete everything**.

Text from a model is treated as text. Raw HTML in an answer is not interpreted, remote images are not loaded (the link is shown instead), and links open in your browser, never inside ZHU's window.

## Resume

Upload a PDF, a Word document (.docx), a text file, or a picture of the page (PNG, JPEG, WebP) in the panel on the right. The engine reads the text out of it once, up to 24,000 characters, and keeps that text and the file (`engine/zhu_engine/resume.py`):

* **PDF**: the text layer (pypdf). A scan has none: then the pictures on its first 10 pages are read with the text recognition built into Windows (`engine/zhu_engine/ocr.py`, Windows.Media.Ocr), on this computer, in the languages installed for your Windows account. Small pictures are enlarged first. The card then says "read from a picture", and the text opens for checking right after the upload.
* **Word**: the document's paragraphs and tables in order, then the page header (where templates put the name and contact details) first and the footer last, each line once. Text boxes are read once, after the paragraph they are anchored to (Word stores each text box twice: a drawing and an older copy for old programs). Text deleted with tracked changes is left out.
* **Pictures**: the same Windows text recognition.

One resume is kept: uploading another replaces it (file and text). The file itself is kept too, in `data\resume\`, so the card opens it as it was uploaded: a PDF or a picture is shown as it is, a Word file as the text read from it (what models and chat sites receive), with **Open in Word** for its layout. A resume uploaded before files were kept shows its text until it is uploaded again. The engine still accepts corrections to the text (`PATCH /api/resumes/{id}`), but the app no longer offers an editor: to change the resume, upload a corrected file.

**The job.** Beside the resume, the job's card takes a title and the job description, pasted or read from a file (up to 12,000 characters). While its own switch is on, it goes with the resume, and the instruction adds: connect the user's experience to what this role asks for, without claiming anything the resume does not state. With the resume switched off, the job goes alone.

**Read once, condensed once.** Models keep nothing between requests, so whatever they should know about you has to go with every message. What goes is not the whole resume: right after the upload, one request to the Custom chat's model (or the first connected one) condenses it into a short profile of at most about 300 words (every role with its dates and its main results with their numbers, projects, skills, education; names, numbers and dates copied exactly; nothing added). The profile is kept with the resume and used until its text changes (a new upload); it is never made again for the same text. A long job description (250 words and more) is condensed the same way into a brief. A resume under 400 words goes as it is. Until the profile exists (the model was busy, or none was connected at upload), the full text goes, and the profile is made after the next Custom chat answer, or with **Make it again** in the resume's preview, which shows exactly what models receive. Chat websites still get the whole resume, once per new chat: there it is sent once and the site keeps it for that chat.

Nothing about the resume is hard-coded. There is no list of "profile questions", no keyword matching and no prepared answers. While the resume is switched on, its profile (or its text, while there is no profile) is appended to the system prompt of every request (Custom chat messages, and questions submitted through `POST /api/providers/{id}/submit`) with one instruction: answer questions that are about the user from the resume, in the first person, using only what it states, and leave it out of everything else. The model decides, per question, whether it is about the user and which parts are relevant. The switch on the resume card stops it being sent without deleting it. Chat websites get the same text and instruction with the first question of each new chat (WEB_CHATS.md).

**Caching.** The system prompt (where the profile and the brief are) is the same, word for word, at the start of every request, and the conversation so far follows it unchanged. On Claude both are marked for prompt caching: the system prompt, and the end of the earlier turns, so each new message reuses everything before it (the first words come sooner, and that part costs a tenth; a part shorter than the model's minimum, 1,024 tokens, is simply not cached, which a short profile alone usually is). The answer's usage records `cache_read_input_tokens`. OpenAI, DeepSeek and Gemini cache a repeated start of a request by themselves; because it never changes, it is the part they reuse.

Live check with a made-up resume and `kilo-auto/free`: "Tell me about yourself, and what was your biggest impact at your current job?" was answered in the first person with the resume's own facts (role, employer, the latency figures); the next question, about mutexes and semaphores, was answered without any mention of it.

## How it works

```text
ChatPane (features/chat) ── POST /api/chats/{id}/messages {provider_id, model, content | regenerate}
        ▲                              │
        │ chat.delta / chat.completed  ▼
   useChat store  ◄── WebSocket ── SessionService.chat_send → adapter.stream_response
```

* Engine: `SessionService.chat_*` in `engine/zhu_engine/session.py`; routes `GET/POST /api/chats`, `GET/PATCH/DELETE /api/chats/{id}`, `POST /api/chats/{id}/messages`. One answer streams per conversation at a time (409 otherwise). Cancelling uses the existing `POST /api/requests/{id}/cancel`.
* Context (`_chat_history`): the last 40 messages within 120,000 characters, always starting with a user turn. An answer that failed before any text arrived is left out together with its question, so roles alternate. A model's thinking is never sent back.
* Thinking: the OpenAI-compatible adapter turns `reasoning` / `reasoning_content` deltas into `reasoning` events. The chat stores them inside a leading `<think>…</think>` block.
* Events: `chat.delta`, `chat.completed`, `chat.error` (`status` is `failed` or `cancelled`), `chat.updated`, `chat.deleted`. An answer still streaming when the engine stops is marked `cancelled` on the next start, keeping the text that had arrived.
* Front end: `ChatPane` (header, message box), `Messages` (bubbles, scroll following), `Markdown` (react-markdown with GFM, KaTeX and highlight.js), `ModelPicker`, and the pure helpers `models.ts` and `chatText.ts`. The pane is a separate chunk that loads with the first chat tab.
* Scrolling: while you are at the bottom the view follows the answer; once you scroll up it stays put and a **Latest** button brings you back.

### Typing and scrolling (Custom chat, live transcript)

Text reaches the window in bursts: the engine passes on what the model wrote about 20 times a second, and models write unevenly. Three pieces make it read like typing and scroll smoothly:

* **Typewriter** (`utils/typewriter.ts`, `hooks/useTypewriter.ts`). The visible part closes the gap to the text that has arrived exponentially (time constant 0.3 s): a model writing steadily is shown at its own speed, 0.3 s behind; a burst is spread over the next frames; a pause slows the text instead of stopping it dead; a finished answer drains in about half a second; never slower than 45 characters a second. Steps depend on elapsed time, not on frames, so a slower screen shows the same speed. Text already there when a view opens (history) is not typed again. One animation-frame loop runs only while text is behind, with a timer in its place when no frames come (a minimized window). Reduce motion shows text at once.
* **Block-by-block Markdown** (`features/chat/markdownBlocks.ts`). The answer is cut into top-level blocks at blank lines, never inside code, formulas, a list or an indented continuation (and not at all when it defines link references), and each block is rendered and memoized on its own. While an answer is written only its last block is parsed again, so an update costs one paragraph however long the answer is: measured on a 4,200-character answer with code, tables and formulas, 11 ms a median update before (17 ms near the end, more than a 60 Hz frame) and 1.8 ms after (2 ms near the end). The last block is tidied while it is written: `**`, `` ` `` and `~~` are closed, a link shows its text until its address is complete, and a table or `$$` formula appears once it can be drawn. A long code block is redrawn less often (at most every 100 ms) while it grows.
* **Follow scroll** (`hooks/useStickToBottom.ts`). A ResizeObserver on the content starts a glide toward the bottom (exponential ease, 90 ms, frame-rate independent) that new text extends rather than restarts. The wheel, the keyboard, a touch or the scrollbar stop it at once; back at the bottom, following resumes. A view opens at its end without gliding; a message you send glides into view.

## Tested

`engine/tests/test_chat.py` (free-model detection, model-list shapes, context building, a full conversation against a local gateway-like server: two turns with two models, answer again, a provider error and the retry, thinking, rejected requests, purge and interrupted answers) and `apps/desktop/tests/chat.test.tsx` (model list and default choice, text preparation, the rendered Markdown, the store, questions reaching the chat's message box).

Live on 2026-11-20, front end in a browser against a development engine with throwaway data: Start without a key (Kilo Gateway: 14 free models found), a streamed answer with thinking, code, a table and a formula from `kilo-auto/free`, stop, try again, reopening the conversation after a reload, and adding the same gateway as a custom provider ("14 of them free", a free model selected). **Not tested: the providers that need a key** (SambaNova, NVIDIA NIM, Z.ai and the earlier ones); their addresses and free tiers come from their documentation.
